# Архитектура и решения

Решения приняты 10 ноября 2026 года. Различайте выбранную архитектуру и подключённые возможности.

## 1. Одно приложение с общим API

Выбраны TypeScript и Next.js App Router на Node.js 22. Один репозиторий, один пакет pnpm, один деплой. Это сокращает настройку без привязки будущих мобильных клиентов к React или серверным функциям Next.js.

```text
Веб-клиент / будущие Android и iOS
              ↓ HTTP JSON
Route Handlers: /api/v1
              ↓
Серверная прикладная и предметная логика
              ↓
Drizzle → PostgreSQL
```

Обработчик HTTP отвечает за транспорт, проверку входных данных и авторизацию. Бизнес-правила находятся в `src/server`, типы публичного API — в `src/contracts`. Клиентский код не импортирует серверные модули, секреты и схему БД. Веб использует тот же API для операций дневника, что и будущие приложения; Server Actions не становятся единственным интерфейсом продукта.

Микросервисы, отдельный API-процесс, монорепозиторий и универсальный мобильный UI сейчас не нужны. Разделение слоёв позволит выделить сервер позднее при реальной необходимости.

## 2. Публичные интерфейсы

Health: `GET /api/v1/health`: `200`, JSON `{"status":"ok"}`, без проверки базы, секретов и внешних сервисов. Это liveness-проверка процесса, а не готовности базы. Ответ не кешируется.

OpenAPI 3.1 доступен как `/openapi.json`; он описывает только работающий контракт. Изменения API сопровождаются изменениями спецификации и сквозными тестами. Продуктовые маршруты и форматы ошибок будут добавляться вместе с соответствующей функциональностью, без фиктивных заглушек в API.

Авторизация обслуживается Better Auth под `/api/auth`; это отдельный протокол библиотеки. Продуктовый API включает `/api/v1/me`, управление сессиями, `/activate` и `/admin/*`; все реализованные операции описаны в OpenAPI.

## 3. Хранение и аккаунты

PostgreSQL 17, Drizzle и Better Auth подключены. Схема включает пользователей, способы входа, сессии, проверки, лимиты, допуски email, активации, глобальный режим регистрации и аудит. Drizzle-миграции хранятся в Git и применяются отдельной командой. База не требуется во время сборки; серверные объекты создаются лениво при обращении.

Поддержаны Google и email/пароль. Неявная привязка одинакового email отключена; дополнительный провайдер подключается из авторизованного кабинета. Для пароля требуется подтверждённый адрес. Google требует подтверждённый провайдером email. OAuth-токены шифруются Better Auth, одноразовые токены активации хранятся только в виде SHA-256.

Роли и блокировка проверяются в PostgreSQL при защищённых запросах, cookie-кеш сессий отключён. Административные изменения сериализуются блокировкой глобальной строки настроек; в транзакции повторно проверяется инициатор. Изменения ролей, блокировка и сброс пароля отзывают сессии. Публичные методы Better Auth также проходят правила допуска и защиту привилегированных полей.

CSRF: изменяющие продуктовые и auth-запросы требуют точного Origin; OAuth использует состояние и PKCE Better Auth. Лимиты находятся в базе и согласованы между экземплярами. Личные ответы не кешируются. Пул PostgreSQL ограничен пятью соединениями на процесс; для Vercel нужен близкий регион базы и подходящий внешний пул.

Локальная среда — Compose PostgreSQL + Mailpit. Внешние письма не отправлялись. Тесты используют настоящий PostgreSQL, локальный перехват почты и OAuth-провайдер, доступный только в NODE_ENV=test. Инструкции и ограничения — в [accounts.md](accounts.md).

## 4. Локализация и интерфейс

next-intl, адреса `/ru` и `/en`, русский по умолчанию. Автоопределение по заголовку браузера отключено, чтобы старт был предсказуемым. API и статические файлы не проходят через локализующий proxy. Переводы — в `messages`, ключи одинаковы в обоих языках; язык документа соответствует маршруту.

Стартовая страница — Server Component, без глобального состояния и обязательного клиентского провайдера. Для небольшого каркаса достаточно обычного CSS с переменными цветов и отступов; библиотеку компонентов добавляем при появлении форм и сложного взаимодействия. Шрифты DIN Pro Condensed и Gotham Pro подключены через `next/font/local`; предоставленные исходники находятся в `src/assets/fonts`, в сборку включены только пять используемых начертаний. Фотографии из `public/images/coffee` отображаются через Next Image с адаптивными размерами. Сборка и отображение не требуют внешних шрифтовых или фотосервисов. Визуальные токены и правила развития интерфейса закреплены в [дизайн-системе](design-system.md).

Переключатель языка использует обычные ссылки и сохраняет текущий раздел и параметры активации. Общие шапка и подвал используются главной и внутренними страницами. Формы, кабинет и админка — изолированные клиентские компоненты с серверной защитой страниц и API; клиентский контекст переводов не требуется. Автоматическое редактирование `AGENTS.md` со стороны Next.js отключено через `agentRules: false`.

## 5. Переносимость и качество

Next.js standalone-вывод используется для Docker. На Vercel работает обычная интеграция Next.js. Нет обязательных Vercel Storage, OAuth-сервиса хостинга или локальной файловой базы.

Строгий TypeScript, ESLint, Prettier, Playwright. Проверки запускаются локально и в GitHub Actions. Версии runtime и менеджера пакетов закреплены; совместимые версии пакетов фиксируются в lockfile. Обновления выполняются отдельными изменениями с повторной проверкой.

ESLint закреплён на совместимой ветке 9: плагины React, import и jsx-a11y из текущей конфигурации Next.js ещё не объявляют поддержку ветки 10. `pnpm-workspace.yaml` используется для политики установки pnpm, а не для монорепозитория: разрешены необходимые build-скрипты `@parcel/watcher`, `@swc/core`, `esbuild` и конкретные платформенные пакеты `@embedded-postgres/*`. Исключения минимального возраста релиза библиотек привязаны к точным версиям. Не разрешайте все сторонние build-скрипты глобально.

Для `pnpm dev` выбран Webpack: в текущем Windows-окружении холодные одновременные запросы к `/ru` и `/en` с Turbopack воспроизводимо давали ошибку чтения JSON, тогда как тот же сценарий с Webpack прошёл. Точная причина не установлена. Production-сборка остаётся на стандартном Turbopack и проверена отдельно. Вернуться к Turbopack для разработки можно после проверки этого сценария на обновлённой версии Next.js.

## Кофейный дневник — 11 ноября 2026 года

Добавлены coffee_items, coffee_sets, coffee_brews, coffee_adjustments и coffee_operations. Запасы хранят количество в целых минимальных единицах; формат определяет граммы или штуки. Набор группирует запасы без отдельного списываемого баланса. Порядок компонентов хранится явно.

`src/server/coffee.ts` содержит валидацию и транзакционные операции. Тонкий обработчик `/api/v1` использует существующую авторизацию, Origin и лимиты. Контракты описаны в `src/contracts/coffee.ts` и OpenAPI. Клиентские компоненты используют только REST; страницы защищены ProtectedScreen. Публичная сборка не подключается к базе.

Изменения сериализуются блокировкой строки владельца; затронутые запасы блокируются в стабильном порядке. Это согласует остатки, состав, повторы и удаление аккаунта при небольшом объёме личного дневника. Версии защищают изменения записей; ключи операций с отпечатком содержимого сохраняют первоначальный результат создания приготовления/корректировки. Подробные правила — в domain.md.

Кофейные данные удаляются каскадно вместе с аккаунтом. Новых сервисов и переменных окружения нет. Миграции применяются только явной командой. Даты без времени не преобразуются через UTC; время приготовления использует часовой пояс браузера.

`pnpm test:coffee` запускает отдельный Playwright-набор на существующем изолированном PostgreSQL/SMTP-стенде. В CI он выполняется после аккаунтов; параллельный запуск этих стендов не поддерживается. Текущие серверные списки фильтруют личные данные в памяти; при росте каталогов следует перенести пагинацию и агрегаты в SQL.
