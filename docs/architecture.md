# Архитектура и решения

Решения приняты 10 ноября 2026 года. Различайте выбранную архитектуру и подключённые возможности.

## 1. Одно приложение с общим API

Выбраны TypeScript и Next.js App Router на Node.js 22. Один репозиторий, один пакет pnpm, один деплой. Это сокращает настройку без привязки будущих мобильных клиентов к React или серверным функциям Next.js.

```text
Веб-клиент / будущие Android и iOS
              ↓ HTTP JSON
Route Handlers: /api/v1
              ↓
Серверная прикладная и предметная логика
              ↓
Drizzle → PostgreSQL (будущий этап)
```

Обработчик HTTP отвечает за транспорт, проверку входных данных и авторизацию. Бизнес-правила находятся в `src/server`, типы публичного API — в `src/contracts`. Клиентский код не импортирует серверные модули, секреты и будущую схему БД. Веб использует тот же API для операций дневника, что и будущие приложения; Server Actions не становятся единственным интерфейсом продукта.

Микросервисы, отдельный API-процесс, монорепозиторий и универсальный мобильный UI сейчас не нужны. Разделение слоёв позволит выделить сервер позднее при реальной необходимости.

## 2. Публичные интерфейсы

Реализован только `GET /api/v1/health`: `200`, JSON `{"status":"ok"}`, без проверки базы, секретов и внешних сервисов. Это liveness-проверка процесса, а не готовности будущей базы. Ответ не кешируется.

OpenAPI 3.1 доступен как `/openapi.json`; он описывает только работающий контракт. Изменения API сопровождаются изменениями спецификации и сквозными тестами. Продуктовые маршруты и форматы ошибок будут добавляться вместе с соответствующей функциональностью, без фиктивных заглушек в API.

Будущая авторизация обслуживается Better Auth под `/api/auth`; это отдельный протокол библиотеки, а не версия продуктового API. Сейчас такого маршрута нет.

## 3. Хранение и аккаунты — выбраны, не подключены

- PostgreSQL: переносимая серверная база, локально/на собственном сервере или у совместимого провайдера.
- Drizzle: SQL-схема, типизированные запросы и миграции, сохраняемые в Git. Автоматические миграции при старте приложения не выполняются.
- Better Auth: аккаунты и сессии, Google как первый и единственный провайдер входа. Для будущего Expo-клиента предусмотрена официальная интеграция; мобильный протокол подключается и проверяется на отдельном этапе.

Пакеты Drizzle, PostgreSQL-драйвера и Better Auth пока не установлены: нет кода, которому они нужны. Нет схем, миграций и обязательных переменных окружения. Подключать их следует на втором этапе вместе с тестами изоляции пользователей и реальным входом.

Следующий этап обязан проверять владельца каждой записи на сервере, защищать операции записи с учётом сессий и CSRF, исключать персональные данные из публичных кешей. Для Vercel потребуется совместимый пул подключений и близкий к приложению регион базы. CORS для мобильных клиентов настраивается по их требованиям позднее; wildcard с credentials не используется.

## 4. Локализация и интерфейс

next-intl, адреса `/ru` и `/en`, русский по умолчанию. Автоопределение по заголовку браузера отключено, чтобы старт был предсказуемым. API и статические файлы не проходят через локализующий proxy. Переводы — в `messages`, ключи одинаковы в обоих языках; язык документа соответствует маршруту.

Стартовая страница — Server Component, без глобального состояния и обязательного клиентского провайдера. Для небольшого каркаса достаточно обычного CSS с переменными цветов и отступов; библиотеку компонентов добавляем при появлении форм и сложного взаимодействия. Внешние шрифты и изображения не нужны для сборки или отображения.

## 5. Переносимость и качество

Next.js standalone-вывод используется для Docker. На Vercel работает обычная интеграция Next.js. Нет обязательных Vercel Storage, OAuth-сервиса хостинга или локальной файловой базы.

Строгий TypeScript, ESLint, Prettier, Playwright. Проверки запускаются локально и в GitHub Actions. Версии runtime и менеджера пакетов закреплены; совместимые версии пакетов фиксируются в lockfile. Обновления выполняются отдельными изменениями с повторной проверкой.
