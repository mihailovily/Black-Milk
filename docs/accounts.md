# Аккаунты и администрирование

## Настройка

Нужны Node.js 22, pnpm 11.25.0 и PostgreSQL 17. Compose поднимает PostgreSQL и Mailpit с портами только на `127.0.0.1`. На собственной машине сначала установите и запустите Docker Desktop с Linux-контейнерами.

```sh
pnpm install --frozen-lockfile
pnpm setup:local
docker compose --env-file .env.local up -d
pnpm db:migrate
pnpm admin:bootstrap --email your-address@example.com
pnpm dev
```

Служебная команда резервирует допуск и назначение первого администратора. Чужой неподтверждённый email не даёт прав: владелец регистрируется и подтверждает адрес письмом либо входит через Google с подтверждённым адресом. У уже подтверждённого аккаунта роль меняется сразу. При существующем активном администраторе команда отказывается выполнять повторное назначение; дальнейшие роли меняются через админку.

Письма доступны на `http://localhost:8025`. Это локальный перехватчик: реальной внешней отправки нет. После подтверждения email войдите на `/ru/sign-in`; кабинет — `/ru/account`, безопасность — `/ru/account/security`, админка — `/ru/admin/users`. Английские страницы используют `/en`.

`setup:local` не перезаписывает `.env.local`. При существующей конфигурации редактируйте её самостоятельно по `.env.example`. Генерируйте случайный `BETTER_AUTH_SECRET` длиной не менее 32 символов; одинаковый секрет используется всеми экземплярами одного окружения. Примерные значения `replace-*` не принимаются. Параметры базы и почты остаются серверными, без `NEXT_PUBLIC_`.

## Google OAuth

В Google Cloud создайте OAuth-клиент типа Web application. Настройте экран согласия и тестовых пользователей, если приложение в тестовом режиме. Для локального `BETTER_AUTH_URL=http://localhost:3000` разрешённый redirect URI — `http://localhost:3000/api/auth/callback/google`. Для production используйте точный HTTPS-адрес своего домена. Добавьте `GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET` в серверное окружение и перезапустите приложение.

Адрес приложения фиксируется через `BETTER_AUTH_URL`; `localhost` и `127.0.0.1` считаются разными origin. Используйте адрес, указанный в конфигурации. Не разрешайте произвольные preview-домены или wildcard redirect URI. Реальный Google-вход требует ручной настройки проекта Google; тестовый провайдер его не заменяет.

Для существующего аккаунта с тем же email автоматическая привязка Google отключена. Сначала войдите прежним способом и выберите «Подключить Google» в безопасности. Другой email привязать нельзя. Пользователь Google может добавить пароль через письмо восстановления; сброс пароля завершает все старые сессии. OAuth-токены шифруются средствами Better Auth.

## Регистрация и активация

Режим по умолчанию — `invite-only`. Администратор добавляет email в «Допуски»: после этого владелец может зарегистрироваться через пароль или Google. Отзыв допуска отменяет ожидающую активацию, но не блокирует уже созданный аккаунт. Для существующего пользователя есть отдельная блокировка.

«Создать пользователя» создаёт допуск и ожидающую активацию запись с именем и email. Пользователь получает одноразовую ссылку на 24 часа и сам устанавливает пароль. В базе хранится SHA-256 токена; сам токен возвращается только в почтовом сообщении. Повторная отправка заменяет токен, предыдущая ссылка становится недействительной. Сбой доставки не создаёт активный аккаунт: запись остаётся для повторной отправки.

Обычная регистрация по паролю требует отдельного подтверждения email. Переключатель «Открыта для всех» влияет на новые регистрации обоими способами, сохраняя доступ существующих аккаунтов. Регистрация, активация и вход проверяются сервером, включая прямые вызовы Better Auth.

## Административные операции

Роли — `user` и `admin`. Пользователь меняет только отображаемое имя; email и аватар здесь не редактируются. Самостоятельное удаление аккаунта не включено.

Администратор управляет профилями, ролями, блокировками, сессиями, приглашениями и режимом регистрации. Блокировка и изменение роли отзывают старые сессии. Заблокированному пользователю нельзя войти до разблокировки; разблокировка не восстанавливает старые сессии. Продвижение неподтверждённого аккаунта в администраторы запрещено.

Собственное удаление, блокировка и понижение роли через админку запрещены. Изменения доступа и удаления сериализуются блокировкой строки глобальных настроек PostgreSQL. Внутри транзакции повторно проверяются действующие полномочия инициатора и наличие активных администраторов.

Удаление требует совпадения email. Удаляются пользователь, связанные аккаунты провайдеров, сессии, допуск, активация и связанные записи проверки. В журнале удаляются идентифицирующие email и ссылки на удалённого пользователя; остаётся обезличенное событие. Резервные копии PostgreSQL имеют отдельную политику хранения и не очищаются этим действием.

## API и эксплуатация

Better Auth обслуживает `/api/auth`. Продуктовые интерфейсы описаны в `/openapi.json`: `/api/v1/me`, сессии, `/activate` и `/admin/*`. Изменяющие запросы требуют `Origin`, точно равного настроенному origin приложения. Роли и блокировка проверяются в базе, кеш сессий выключен; личные ответы имеют `Cache-Control: no-store`. Секреты сессий не возвращаются административным интерфейсом.

Лимиты Better Auth хранятся в PostgreSQL. Дополнительно общий лимит записей авторизации — 120 запросов в минуту, операций пользователя — 60, публичной активации — 20. Дополнительно действуют лимиты по нормализованному email: 10 входов или 5 запросов регистрации/восстановления/подтверждения в минуту. Общие анонимные лимиты согласованы между экземплярами и не зависят от подменяемых заголовков IP. Для масштабирования их можно пересмотреть вместе с доверенным reverse proxy.

Внешняя почта не настраивается автоматически. В production без почтового транспорта соответствующие операции возвращают `MAIL_UNAVAILABLE`. Сборка и публичная главная доступны без базы; защищённые страницы показывают состояние недоступности. Health проверяет только процесс. До публичного запуска проверьте внешний SMTP, реальный Google OAuth, TLS, резервное копирование и восстановление.

## Проверки

```sh
pnpm test:integration
pnpm build
pnpm test
pnpm test:accounts --workers=1
```

Без `TEST_DATABASE_URL` создаётся временный настоящий PostgreSQL 17 в `.local`, без служб и системных пользователей. При завершении тестов кластер останавливается и данные удаляются. Можно указать отдельную тестовую базу с именем, оканчивающимся на `_tests`; её `public` схема пересоздаётся. Рабочие базы запрещены.

Интеграционные тесты используют перехват писем в памяти и локальный OAuth-сервер. Он доступен только при `NODE_ENV=test`, не включается в production даже с `TEST_OIDC_URL`. Браузерные тесты запускают отдельный PostgreSQL, тестовую SMTP-почту и production-сборку на 3100; порты 3101/3102 используются только локальными фикстурами. Google в этой production-сборке не подменяется.
