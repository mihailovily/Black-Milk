# Запуск и размещение

Каркас работает без базы и Google-входа. Размещение здесь описано как инструкция; сама инициализация не создаёт облачные ресурсы и не публикует приложение.

## Локальная разработка и Node.js

Node.js 22.19+ (ветка 22), pnpm 11.25.0. Из корня проекта:

```sh
pnpm install --frozen-lockfile
pnpm dev
```

Production-запуск на собственном сервере:

```sh
pnpm install --frozen-lockfile
pnpm build
pnpm start
```

Приложение слушает порт 3000. `PORT` можно задать в окружении процесса. Перед приложением нужен reverse proxy с HTTPS, например Caddy или nginx; на публичном сервере настройте перезапуск процесса и ограничьте прямой доступ к внутреннему порту. Пользовательские файлы или данные в файловую систему приложения не записываются.

## Docker

Нужен установленный и запущенный Docker с Linux-контейнерами. Сборка требует доступа к реестрам Node.js/pnpm; работающий контейнер не требует внешних сервисов.

```sh
docker build -t black-and-milk:local .
docker run --rm --name black-and-milk -p 127.0.0.1:3000:3000 black-and-milk:local
```

Откройте `http://localhost:3000/ru`, `/en` и `/api/v1/health`. Остановить контейнер из другого терминала: `docker stop black-and-milk`.

Многоэтапная сборка устанавливает зависимости по lockfile, создаёт standalone-вывод и запускает его от непривилегированного пользователя. В финальный образ копируются standalone, статические ресурсы Next.js и `public`. В Docker-контекст не попадают `.git`, локальные секреты, зависимости и результаты тестов. Для production используйте сохранённый тег образа и HTTPS reverse proxy. Контейнер имеет liveness-проверку `/api/v1/health`.

## Vercel

1. Опубликуйте репозиторий в своём Git-провайдере и импортируйте его в Vercel либо используйте свой обычный процесс размещения. Это отдельное действие, не выполненное в рамках инициализации.
2. Framework Preset: Next.js. Корень проекта: корень репозитория. Node.js: 22.x.
3. Install Command: `pnpm install --frozen-lockfile`. Build Command: `pnpm build`. Output Directory оставьте стандартным для Next.js; не указывайте `.next/standalone` вручную.
4. Для текущего каркаса не добавляйте Google-ключи или `DATABASE_URL`: они не используются.
5. После размещения проверьте `/ru`, `/en`, переключение языка, `/openapi.json` и `/api/v1/health` на адресе размещения.

## Переменные окружения

Сейчас обязательных переменных нет. `.env.example` содержит закомментированные будущие параметры:

- `DATABASE_URL` — PostgreSQL, позднее с пулом подключений для выбранного хостинга.
- `BETTER_AUTH_SECRET` — серверный секрет сессий.
- `BETTER_AUTH_URL` — внешний адрес приложения.
- `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` — Google OAuth.

После реализации входа потребуется настроить разрешённые origin и redirect URI в Google Cloud. Предполагаемый callback Better Auth: `/api/auth/callback/google`; окончательный адрес проверяется при подключении. Секреты остаются серверными, без префикса `NEXT_PUBLIC_`, не попадают в Git, Docker-образ или логи. Для разработки, preview и production используются отдельные настройки.

## Будущая база

Используйте обычный PostgreSQL на своём сервере или совместимый управляемый сервис. Для Vercel выбирайте регион базы рядом с приложением и подключение с подходящим пулом. Миграции запускаются отдельным шагом выпуска с резервной копией и проверкой результата; не при каждом холодном старте. Точный порядок появится вместе с реализацией базы.

## Проверки после размещения

Health API проверяет только доступность приложения и возвращает `{"status":"ok"}`. Он пока не гарантирует доступность базы или возможность входа. После подключения этих функций добавить отдельные проверки готовности и полный сценарий входа/записи. Резервное копирование и восстановление базы обязательны до публичного запуска.
